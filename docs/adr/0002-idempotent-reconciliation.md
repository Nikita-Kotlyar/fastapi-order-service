# ADR 0002: детерминированная идемпотентная сверка

## Status

Accepted.

## Context

Выгрузки приходят повторно, частично пересекаются и содержат дубли. Ручной
разбор проблем и ручные заказы не должны теряться при пересборке витрины.
Повторный запуск должен давать те же canonical ID и те же issue keys.

## Decision

1. Canonical ID присваиваются в детерминированном порядке обхода источников.
2. Issue key — SHA-1 от типа, источника, source_id, canonical ID и деталей.
3. При повторной сверке сгенерированные заказы пересобираются, а ручные
   заказы `CO-MAN-*` сохраняются.
4. Статусы issue `resolved` / `ignored` переносятся по стабильному issue key.
5. Импортные батчи фиксируются с SHA-256 и raw-записями для аудита.

## Consequences

- Повторный ingest и reconcile не создают дублей.
- Ручные решения аналитика не теряются.
- Изменение правил матчинга может изменить canonical ID; это осознанный
  breaking change, который фиксируется в changelog.
- История импортов растёт; для production нужна политика архивирования.
